## 修复评估标准

在评估每个问题的修复必要性时，考虑以下因素：

| 因素 | 权重 | 说明 |
|------|------|------|
| 维护成本 | 30% | 修复后能否降低维护难度 |
| 风险程度 | 25% | 当前代码是否容易引发 bug |
| 开发效率 | 20% | 修复后能否提升开发速度 |
| 性能影响 | 15% | 修复是否改善性能 |
| 必要性 | 10% | 是否是功能性需求 |

**评分标准：**
- 8-10 分：✅ 强烈建议修复
- 5-7 分：⚠️ 建议评估后决定
- 0-4 分：❌ 暂不需要修复

**修复方案：**

#### 方案 A：保留 store，删除 service（推荐）

```
步骤：
1. 检查 fileService.ts 的所有使用者
2. 将使用者迁移到 fileExplorer store
3. 删除 fileService.ts
4. 验证功能正常
```

**具体操作：**

```bash
# 1. 搜索 fileService 使用者
grep -r "from.*fileService" src/

# 2. 检查 service 中的函数是否被单独调用
```

### 2.4 事件总线与 Store 混用

**评估分数：** 5/10

**修复必要性分析：**

| 因素 | 得分 | 说明 |
|------|------|------|
| 维护成本 | 2 | 需要追踪两种更新路径 |
| 风险程度 | 2 | 可能导致状态不一致 |
| 开发效率 | 1 | 开发者需要理解何时用哪种 |
| 性能影响 | 0 | 无差异 |
| 必要性 | 0 | 功能上可以工作 |

**修复方案：**

1. **审计事件总线使用**

```bash
# 统计事件类型
grep -r "AppEvents\." src/ | sort | uniq

# 检查事件监听
grep -r "eventBus\.on" src/
```

2. **制定规范：**
   - Store 是单一数据源
   - 事件总线仅用于跨组件通信（如通知）
   - 不再用于状态同步

3. **逐步迁移：**

```typescript
// 迁移前
eventBus.on(AppEvents.CONTENT_CHANGED, handler)
tabsStore.updateTab(...)

// 迁移后
tabsStore.updateTab(...)  // 直接更新
// 移除 CONTNET_CHANGED 事件的监听
```

**预估时间：** 1-2 天（需要全面测试）
