# 风险与回滚方案

## 一、风险清单

| 编号 | 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|------|---------|
| R1 | 重构引入回归 Bug | 高 | 高 | 每阶段先补测试，重构后全量回归 |
| R2 | 事件总线统一后监听器丢失 | 中 | 高 | 搜索所有 `eventBus.on` 调用点，逐一迁移验证 |
| R3 | 双层 Store 消除后数据不一致 | 中 | 高 | 保留旧 Store 作为只读缓存，新 Store 独立验证后再删除 |
| R4 | DI 容器改造导致初始化顺序问题 | 中 | 中 | 保持 Composition Root 位置不变，只改绑定方式 |
| R5 | Command Handler 重构导致快捷键失效 | 低 | 高 | E2E 测试覆盖所有 55 个命令的快捷键 |
| R6 | 团队成员不熟悉新模式 | 中 | 中 | 每阶段产出迁移指南 + 代码模板 |
| R7 | 某阶段超时影响整体进度 | 中 | 中 | 每阶段设置 deadline，超时则跳过非关键子任务 |

---

## 二、回滚原则

- **Git 策略**: 每个阶段一个独立分支，合并前必须通过全量测试
- **阶段隔离**: 每个阶段完成后打 `git tag`，格式 `refactor/phase-N`
- **原子回滚**: 如某阶段失败，`git reset` 到上一个 tag 即可恢复

---

## 三、各阶段回滚方案

| 阶段 | 回滚方式 | 回滚影响 | 恢复时间 |
|------|---------|---------|---------|
| P0 基础设施 | `git revert` 到 `main` | 无（纯增量） | 即时 |
| P1 ISP 拆分 | `git reset` 到 `refactor/phase-1` | 仅 IEditorProvider 相关文件 | <5 分钟 |
| P2 Store 解耦 | `git reset` 到 `refactor/phase-2` | Store 恢复旧逻辑 | <5 分钟 |
| P3 事件统一 | `git reset` 到 `refactor/phase-3` | 事件通信恢复旧模式 | <5 分钟 |
| P4 命令重构 | `git reset` 到 `refactor/phase-4` | 命令系统恢复旧实现 | <5 分钟 |
| P5 CQRS + Mediator | `git reset` 到 `refactor/phase-5` | 数据流恢复旧路径 | <10 分钟 |
| P6 Composable 拆分 | `git reset` 到 `refactor/phase-6` | Facade 恢复为 useAppContext | <5 分钟 |
| P7 DI 修复 | `git reset` 到 `refactor/phase-7` | DI 恢复旧绑定方式 | <5 分钟 |

## 四、紧急回滚流程

```bash
# 1. 标记当前状态（保留现场）
git tag refactor/phase-N-failed

# 2. 回滚到上一个稳定版本
git reset --hard refactor/phase-N-1

# 3. 验证回滚后可运行
npm run test:run
npm run dev

# 4. 推送回滚
git push origin main --force-with-lease
```
