# 架构模式选型与约束

## 一、当前项目已采用的架构

本项目已采用 **Clean Architecture + Hexagonal Architecture (Ports & Adapters)**：
- `src/core/` 是纯业务核心，不依赖任何外部框架
- `src/adapters/` 是薄胶水层，桥接核心与具体技术
- `src/infrastructure/` 是技术实现和 DI 容器
- `src/stores/` + `src/components/` 是 Vue 表现层

依赖方向严格单向：**Presentation → Adapters → Core（内层）**

## 二、本次重构引入的 3 个新模式

### 模式 1：CQRS（Command Query Responsibility Segregation）

**解决的问题**：
- 读写混在一起，Store 同时承担查询和命令职责
- 双层 Store（adapters/stores 包装 stores）导致每次访问创建 N 个对象
- Store 中嵌入业务逻辑（UUID 生成、邻居选择、事件发送）

**改法**：
```
当前：Component → useAppContext → Store（读写混合）→ 双层Adapter
改后：Component → Query（直接读Store）/ Command（走Use Case写Store）
```

- **写操作**（CreateTab, SaveFile, DeleteFile）：Command → Use Case → Repository 写入 → eventBus.emit
- **读操作**（GetTabs, GetActiveTab）：Query → Repository 直接读 → 返回 Entity
- Store 变为纯数据容器，不含业务逻辑
- 消除双层 Store 适配器

### 模式 2：Mediator（中介者模式）

**解决的问题**：
- Command Handler 3 种通信机制混用（eventBus / CustomEvent / document.execCommand）
- `useAppContext()` 216 行 God Object，暴露 80+ 属性
- 团队调用方式不一致，组件直接 import Store

**改法**：
```
当前：Component → useAppContext（God Object）→ 直接调Store/Use Case/EventBus/CustomEvent
改后：Component → useXxxContext（按领域拆分）→ Mediator.send(Command/Query) → 统一处理
```

- 所有组件不直接调用 Store/Use Case，统一通过 Mediator
- 拆分 `useAppContext()` 为：`useTabContext()`, `useFileContext()`, `useEditorContext()`, `useSearchContext()`
- 统一通信机制：消除 CustomEvent 和 execCommand，全部走 eventBus

### 模式 3：Interface Segregation Principle（接口隔离）

**解决的问题**：
- `IEditorProvider` 30+ 方法，违反 ISP
- 消费者被迫依赖它不需要的方法
- 3 个 `@deprecated` 方法仍在接口中

**改法**：拆分为 6 个小接口：

| 新接口 | 职责 | 方法数 |
|--------|------|--------|
| `IEditorLifecycle` | 生命周期 | 4 |
| `IEditorTabManager` | Tab 管理 | 4 |
| `IEditorContent` | 内容读写 | 5 |
| `IEditorEventSource` | 事件订阅 | 2 |
| `IEditorView` | 视图控制 | 9 |
| `IEditorTheme` | 主题切换 | 1 |

消费者只依赖它需要的接口，组合接口 `IEditorProvider` 保留向后兼容。

## 三、三模式协作关系

```
┌──────────────────────────────────────────────────────────┐
│                    组件层 (Vue SFC)                         │
│  useTabContext() / useFileContext() / useEditorContext()    │  ← 按领域拆分的 Facade
└───────────────┬──────────────────────────────────────────┘
                │ Mediator.send(Command | Query)
┌───────────────▼──────────────────────────────────────────┐
│                Mediator（中介者）                           │
│  统一入口，路由 Command/Query 到对应 Handler                  │  ← 消除 God Object
└──────┬──────────────────────────┬────────────────────────┘
       │ Command                  │ Query
┌──────▼──────────┐      ┌───────▼──────────┐
│   Use Cases     │      │   直接读 Repository │  ← CQRS 读写分离
│  (写操作)        │      │  (读操作)          │
└──────┬──────────┘      └───────┬──────────┘
       │                         │
┌──────▼─────────────────────────▼──────────┐
│        Repository / Gateway (Adapter)       │
│  实现多个小接口 (ISP)                         │  ← 接口隔离
└────────────────────────────────────────────┘
```

## 四、架构约束规则（团队强制执行）

### 4.1 目录结构约定

```
src/
  core/                    # 核心层：纯业务逻辑
    entities/              # 领域实体（含业务方法）
    domain/ports/          # 接口定义（Port）
      editors/             # 编辑器小接口（ISP 拆分后）
      gateways/            # 基础设施端口
      repositories/        # 数据仓储端口
      queries/             # CQRS 查询接口
      IMediator.ts         # 中介者接口
    use-cases/             # 用例（每个一个类，一个 execute 方法）
  adapters/                # 适配层：薄胶水
    gateways/              # Gateway 实现
    stores/                # （CQRS 后删除，Store 直接实现 Port）
    composables/           # 按领域拆分的 Facade
    mediator/              # Mediator 实现
      handlers/            # Command/Query Handler
  infrastructure/          # 基础设施：DI、技术实现
    di/                    # InversifyJS 容器
    adapters/editors/      # MilkdownAdapter
  stores/                  # Pinia Store（纯数据容器，直接实现 Repository 接口）
  commands/                # 命令系统
    handlers/              # 按领域拆分的 Handler
  events/                  # 事件总线
  composables/             # UI 组合函数
```

### 4.2 编码规则（ESLint 强制）

| 规则 | 说明 | 阶段 |
|------|------|------|
| 禁止直接导入 `@/events/eventBus` | 必须通过 EventBusGateway | P0 warn → P7 error |
| 禁止直接导入 `@/stores/tabs` | 必须通过 ITabRepository | P0 warn → P7 error |
| 禁止直接导入 `@/stores/preferences` | 必须通过 IPreferencesRepository | P0 warn → P7 error |
| 禁止直接导入 `@/stores/search` | 必须通过 ISearchRepository | P0 warn → P7 error |
| Store 文件不允许包含业务逻辑 | 业务逻辑必须在 Use Case 中 | P2 验证 |
| Command Handler 文件 ≤80 行 | 超过必须拆分 | P4 验证 |
| 新增 Port 接口不超过 8 个方法 | 超过必须拆分为多个接口 | P1 验证 |

### 4.3 团队协作约定

1. **新增功能**：先写 Use Case，再写 Handler，最后接 UI
2. **修改 Store**：只能改数据操作，不能加业务逻辑
3. **新增事件**：必须在 `AppEvents` 中注册，不允许硬编码字符串
4. **新增接口**：放在 `src/core/domain/ports/` 下，不超过 8 个方法
5. **Code Review**：检查是否违反架构规则，拒绝不符合的 PR
